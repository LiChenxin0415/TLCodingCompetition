## 2. 一页速览（TL;DR，读者只需看这一节）

**一句话**：把科技部门已有的「月度绩效合约 100 分制」，升级为「AI 拆解目标 → 自然语言更新进度 → 交付物验证 → 数据核验评分 → 能力画像沉淀」的系统闭环。

**核心概念四件套**

| 概念                 | 定义                                                         |
| ------------------ | ---------------------------------------------------------- |
| 大目标（发布包 Objective） | 中心/组的重点工作或一次发布，例：`核心系统分布式改造一期`                             |
| 合约（Contract）       | 一个员工一个月的绩效合约，`月份 + 权重合计 100%`                              |
| 工作包（Item）          | 合约下的任务项，四类：基础履职/重点交付/治理改善/探索突破；含可量化本月目标 + 约定交付物 + 权重 + 截止日 |
| 交付物（Deliverable）   | 工作包完成时必须上传的产出，类型在制定合约时就已约定                                 |

**必须记住的 6 条硬规则（测试重点）**

1. 合约内工作包 **3–5 个，权重合计必须 = 100%**，否则不允许提交核对。
2. 工作包的「本月目标」**必须含数字 + 时限 + 可验证动词**，否则 AI 体检不通过（可强制提交，但留痕）。
3. 月末评分前，**交付物未上传则该工作包最高 95 分**（"轻微不足"档），不允许 100 分及以上。
4. AI 解析自然语言的进度结果，**默认需人工确认**后才写入；置信度 < 0.6 时不给结论，改让用户选择任务项。
5. 个人月度得分 = `Σ(工作包评分 × 权重) ÷ 100`，**评分区间 80–120**；已发布月份数据只读。
6. 评分偏离 100 分**必须填写评分依据**；发布前必须通过三项前置校验：有效权重 100%、合约与评分全确认、无录入异常。

**优先级**：P0（5 个，构成闭环最小集）→ P1（5 个，管理视图增强）→ P2（1 个，数据积累型增值）。

## 3. 创意与价值：和普通产品差在哪

| 维度    | 普通绩效/任务工具     | 本产品                                                     |
| ----- | ------------- | ------------------------------------------------------- |
| 目标制定  | 让员工填表，写一段话    | **说人话即可**：AI 把口语需求解析成结构化可量化合约（含目标值、交付物、权重、时限）+ 可验证性体检打分 |
| 进度更新  | 手工拖进度条，写"已完成" | **自然语言驱动**：一句话描述今天做了什么，AI 识别归属任务并自动更新进度，同时抽取成果证据        |
| 验收依据  | 截图佐证，组长凭印象    | **交付物前置约定 + 系统数据自动核验**：慢SQL治理直接取治理平台数据，做到位没有由数据回答       |
| 管理者视角 | 只看完成率数字       | **看板可下钻**：效能指标 → 中心/组/个人 → 具体工作包与当日进度，管理动作可落地           |
| 组织沉淀  | 月底打完分就结束      | **能力标签自动生长**：从合约与过程中沉淀个人能力画像，反哺能力辅导与人才盘点（明示不计分）         |

**五个核心亮点（路演必讲）**

1. **AI 落在最脏的环节**：不是聊天机器人，而是把"写目标、报进度"这两件员工最敷衍的事，变成一句话就能完成的动作。
2. **"做到位没有"变成系统约束**：交付物未上传无法拿满分，把题眼写进了代码。
3. **双层进度**：个人工作包进度向上加权汇聚为大目标进度，管理者第一次能看清"大目标真实达成度"。
4. **证据自动核验**：科技部门的工作证据天然长在 DevOps / 工单 / SQL 治理平台里，天然比业务部门更容易做到数据说话。
5. **不异化为考核的能力画像**：能力标签只用于发展辅导、不参与计分，规避组织抵触。

## 4. 背景、目标与用户

- **业务背景**：部门已有成熟的月度绩效合约制度（100 分制、四类任务、3–5 个工作包、月初约定/月中调整/月末评价/中心校准四步流程），但制度靠表格与人工流转，存在三个断点：目标只见工作包不见大目标；进度追踪停留在"做了没有"；验收证据靠人工。

**制度对齐：考核目标四原则 → 产品落点（源自制度图板块 1，产品设计的"宪法"）**

| 考核目标        | 产品落点                               |
| ----------- | ---------------------------------- |
| 聚焦重点、明确方向   | 大目标（发布包）关联 + 优先级字段 + 工作包向上挂接中心月度重点 |
| 结果导向、价值创造   | 可量化本月目标 + 约定交付物 + 数据核验评分           |
| 过程透明、公平公正   | 全流程留痕（进度/变更/解析原文）+ 看板下钻 + 中心尺度校准   |
| 促进成长、共建高效团队 | 能力标签自动生长，仅用于辅导不计分                  |

- **业务目标**：合约全流程线上化率 100%；月末评分依据可追溯率 100%；风险工作包在截止日前 5 天被提前预警。
- **用户目标**：员工 3 分钟内完成一份合规合约；组长核对时每项标准可量化可验证。

| 角色            | 场景                      | 核心痛点                  |
| ------------- | ----------------------- | --------------------- |
| 员工（member）    | 月初定合约、日常报进度、月末传交付物      | 不会写可量化目标；报进度是额外负担     |
| 组长（leader）    | 核对合约、月中调整、月末评分          | 标准不可验证；评分没有依据，尺度难统一   |
| 中心管理者（center） | 看部门效能、确认发布月度结果          | 只能看到汇总数字，看不到数字背后的具体工作 |
| AI 解析服务（系统角色） | 解析合约、解析进度、抽取能力标签、自动取数核验 | 输出必须结构化可校验，失败不能阻塞主流程  |

**职责与权限矩阵（源自制度图板块 7）**

| 角色    | 制度职责                                      | 系统权限                              |
| ----- | ----------------------------------------- | --------------------------------- |
| 中心管理者 | 明确年度重点方向；协调资源与优先级；开展组间评分校准；保障评价公平公正       | 大目标维护；全员数据与看板下钻；校准与确认发布；审计日志导出    |
| 组长    | 制定并确认月度合约；明确成果、时限、权重；及时调整任务并留痕；依据评价结果开展辅导 | 本组成员合约核对/评分/月中调整；本组看板与台账；不可见其他组数据 |
| 员工    | 理解并确认工作约定；按计划高质量完成；及时反馈变化及风险；更新状态与成果证据    | 本人合约与进度更新；交付物/日报周报上传；查看本人历史与最终得分  |

## 6. 用户故事

1. 作为**员工**，我希望用一句话说出本月要干的事就生成合规合约，以便不用绞尽脑汁写"可量化目标"。
2. 作为**员工**，我希望每天用一句话汇报进度就自动更新任务，以便不用额外维护表格。
3. 作为**组长**，我希望核对时系统就告诉我哪条标准不可验证，以便一次对齐不乱改。
4. 作为**组长**，我希望评分依据（交付物 + 平台数据）自动摆在我面前，以便打分有据、组间尺度一致。
5. 作为**中心管理者**，我希望从效能指标一路点到具体某个人某个工作包的进度，以便管理动作能落地。
6. 作为**员工**，我希望看到我的工作包对大目标贡献了多少进度，以便知道自己的工作价值在哪。
7. 作为**部门管理者**，我希望一眼看清部门本月的价值产出与整体效能、一键生成总结报告，以便向公司证明成本部门的价值并完成向上汇报。

## 8. 功能需求详情（P0）

### FR-01 自然语言进度自动更新

**描述**：在工作包提供"说一句"输入框，员工用自然语言描述进展，系统调用 AI 解析为结构化进度更新，人工确认后写入，并同步生成进度留痕。

**输入**：`user_id`、自然语言文本（≤500 字）、可选 `item_id`（已选中时）  
**输出**：变更前后进度、命中的工作包、抽取的成果证据、置信度

**规则**

| 编号 | 规则                                                              |
| -- | --------------------------------------------------------------- |
| R1 | 未指定工作包时，AI 依据文本与用户当月在办工作包标题做匹配，返回最可能的 1 个 + 备选 2 个              |
| R2 | `confidence ≥ 0.6` 才给出结论；`< 0.6` 时只给候选列表，由用户点选                  |
| R3 | 默认**必须人工确认**才写库；确认条文案：`识别为「{工作包}」→ {新进度}%（{+/-}{delta}%），是否采纳？` |
| R4 | 进度区间 0–100，超出则截断并提示；不允许回退超过 20%（防误操作），回退需填写原因                   |
| R5 | 文本中若出现交付完成、验收通过等语义，提示"是否同时上传交付物"（联动 FR-03）                      |
| R6 | 每次解析生成一条 `ProgressLog`，保留原文与解析结果，作为月末评分证据来源之一                   |

**验收标准**

- Given 员工张伟有工作包「核心模块联调」且当前进度 70%，When 他输入"今天联调全部完成，环境问题已解决"，Then 系统在 5 秒内返回解析结果，识别为「核心模块联调」、进度 100%，并展示确认条。
- Given 解析置信度为 0.45，When 解析完成，Then 系统不直接给出进度建议，只展示候选工作包列表供点选。
- Given 用户点击"不采纳"，When 关闭确认条，Then 工作包进度与 ProgressLog 均不发生变化。
- Given 员工输入"今天在忙"，When 解析完成，Then 系统提示"未识别到明确进展"，不产生进度变更。

**异常与空态**

| 场景               | 表现                                   |
| ---------------- | ------------------------------------ |
| AI 超时（>5s）或服务不可用 | 提示"AI 暂不可用，请手动更新进度"，展示手工进度输入框，主流程不阻塞 |
| 用户当月无在办工作包       | 空态："本月暂无在办工作包，请先在合约中添加"，带跳转按钮        |
| 解析出的进度低于当前进度     | 二次确认："将从 {当前}% 回退到 {目标}%，请填写原因"      |

### FR-02 AI 结构化合约生成 + 可验证性体检

**描述**：在合约制定页输入一段口语化的工作描述（或选择关联大目标），AI 输出 3–5 个结构化工作包，并逐条做可验证性体检；员工可编辑后提交。

**AI 输入**：口语描述、关联大目标、该用户近 3 个月历史合约（用于风格与权重参考）  
**AI 输出（严格 JSON）**

```json
{
  "items": [
    {
      "type": "治理改善类",
      "title": "慢SQL治理",
      "target_desc": "治理 10 条，平均耗时下降 30%",
      "deliverable": { "type": "数据报表", "desc": "治理清单 + 治理前后耗时对比报表" },
      "weight": 20,
      "priority": "高",
      "due_date": "2026-10-31",
      "objective_id": "O-001"
    }
  ],
  "total_weight": 100,
  "checks": [
    { "item_title": "慢SQL治理", "has_number": true, "has_deadline": true, "has_verifiable_verb": true, "score": 92, "issues": [] }
  ]
}
```

**规则**

| 编号 | 规则                                                                                  |
| -- | ----------------------------------------------------------------------------------- |
| R1 | 任务类型只能取四类枚举之一：`基础履职类 / 重点交付类 / 治理改善类 / 探索突破类`                                       |
| R2 | 权重为整数百分比，输出后系统自动归一化到 100；若与用户历史权重差异 > 20%，提示确认                                      |
| R3 | 每条工作包必须补齐：可量化目标 + 优先级（高/中/低） + 交付物类型与说明 + 截止日，缺一不可提交核对（对齐制度"同步明确计划截止日、优先级，并完成合约确认"） |
| R4 | 体检得分 = 100 − 扣分项（无数字 −25／无可验证动词 −20／描述过短 −15／无时限 −20／无交付物 −20），低于 80 分标红并要求修改       |
| R5 | 生成结果必须可编辑，AI 生成的工作包标记 `source=AI`，便于后续评估 AI 采纳率                                     |
| R6 | 权重约定需结合任务重要性、难度及责任（对齐制度"重视重点攻坚、工作投入与责任担当"）；AI 生成时将该原则写入提示词约束                        |

**验收标准**

- Given 员工输入"这个月主要搞慢SQL治理和AB需求，再保证生产稳定"，When 点击 AI 生成，Then 8 秒内返回 3 个工作包，权重合计 100%，每条含数字目标、交付物、截止日，并展示体检得分。
- Given 生成结果中某条目标为"提高代码质量"，When 体检执行，Then 该条提示"缺少可量化数字目标、缺少可验证动词"且得分低于 80。
- Given 生成的工作包权重合计为 95%，When 用户点击提交核对，Then 系统拦截并提示"权重合计必须为 100%，当前 95%"。
- Given AI 服务不可用，When 点击生成，Then 提示降级为"手动新增工作包"，并预填模板文案。

### FR-03 交付物约定与上传验收

**描述**：合约制定阶段为每个工作包约定交付物类型与说明；执行阶段员工上传交付物；月末评分时系统校验交付物完整性，未上传的项限制评分上限。

**交付物类型枚举**：`代码合并请求 / 设计文档 / 测试报告 / 数据报表 / 上线单 / PoC 结论报告 / 运维记录 / 其他`

**规则**

| 编号 | 规则                                                                          |
| -- | --------------------------------------------------------------------------- |
| R1 | 工作包创建时交付物类型与说明为**必填**，未填写不允许提交核对                                            |
| R2 | 支持多份交付物（≥1 份即视为已上传），上传形式：本地文件（≤50MB）或外部链接（GitLab MR / 报告链接）                 |
| R3 | 文件类型白名单：pdf/doc/docx/xls/xlsx/ppt/pptx/png/jpg/zip/md/txt；其余拒绝上传            |
| R4 | 月末评分时，**未上传交付物的工作包评分上限 95 分**，界面提示"交付物未上传，最高 95 分"；组长强制打 96 分及以上时需二次确认并填写理由 |
| R5 | 交付物可被组长/中心查看与下载，查看行为记入审计日志                                                  |
| R6 | 合约发布后交付物锁定，不可增删改（防止事后补材料）                                                   |

**验收标准**

- Given 工作包「慢SQL治理」约定交付物为"数据报表"，When 员工点击上传并选择 `治理报告.xlsx`，Then 上传成功，工作包显示"交付物 1/1"，状态变为可评分。
- Given 某工作包未上传交付物，When 组长在评分框输入 100，Then 系统提示"交付物未上传，最高 95 分"，评分被限制为 95。
- Given 上传 `病毒.exe`，When 提交，Then 系统拒绝并提示文件类型不支持。
- Given 合约已发布，When 员工尝试删除交付物，Then 操作被拒绝并提示"已发布合约不可修改交付物"。

### FR-04 大目标关联与进度向上汇聚

**描述**：中心/组维护"大目标（发布包）"，员工合约中的工作包必须关联到一个大目标（除基础履职类可挂空）；系统按权重汇聚出大目标进度并展示各合约包的贡献。


**规则**

| 编号 | 规则                                                                      |
| -- | ----------------------------------------------------------------------- |
| R1 | 大目标字段：名称、所属中心/组、负责人、起止日期、状态（进行中/已达成/已关闭）                                |
| R2 | 工作包关联大目标为单选；`基础履职类`允许不关联，其余三类必填                                         |
| R3 | 大目标进度 = `Σ(关联工作包当前进度 × 工作包权重) ÷ Σ(关联工作包权重)`，保留 1 位小数；无关联工作包时进度为 0 并展示空态 |
| R4 | 大目标详情页必须展示：关联合约包清单（成员、月份、工作包、权重、进度、交付物状态）+ 加权进度 + 贡献占比（单包权重 ÷ 关联总权重）    |
| R5 | 权重合计变化（月中调整）后，大目标进度实时重算                                                 |

**验收标准**

- Given 大目标「核心系统分布式改造一期」关联 3 个工作包，权重 35/30/20，进度 70/33/100，When 打开大目标详情，Then 显示加权进度 = (70×35+33×30+100×20)÷85 = 62.9%，并列出三个合约包及各自贡献占比。
- Given 某大目标无任何关联工作包，When 打开详情，Then 显示空态"当前无合约包关联"，并提供"关联工作包"入口。
- Given 员工把某工作包权重由 20% 改为 30%，When 保存变更，Then 大目标进度立即重算且变更原因进入变更留痕。

### FR-09 月末评价与中心校准

**描述**：月末组长依据"100 分标准 + 实际成果/交付物 + 平台核验数据"逐条评分并填写评分说明；中心校准评分尺度后确认发布。制度图板块 3（评分标准）、板块 6（月度评定流程）、板块 8（Q3 发布条件）在本环节全部落地为系统校验。

**评分档位表（与制度完全一致）**

| 分数    | 档位       | 说明                  |
| ----- | -------- | ------------------- |
| <80   | 严重不足     | 结合本人可归责责任和实际影响评价    |
| 80–89 | 明显不足     | 同上                  |
| 90–94 | 轻微不足     | 同上                  |
| 100   | 完整履约     | 按约定成果、质量和时间完整完成     |
| 105   | 部分超额     | 完整履约基础上，形成可验证的超预期成果 |
| 110   | 显著超额     | 同上                  |
| 120   | 卓越超额（上限） | 同上                  |

**规则**

| 编号 | 规则                                                                             |
| -- | ------------------------------------------------------------------------------ |
| R1 | 评分范围 80–120 整数；**偏离 100 分必须填写评分依据**，依据随台账与看板可追溯                                |
| R2 | 评分 >100（超额档）必须同时满足：①该工作包完整履约 ②存在可验证的超预期成果（证据/核验数据留痕）                           |
| R3 | 超预期认定参考四类：**治理共性问题、提升质量效率、主动担当协同、沉淀长效机制**（辅助判断，不构成穷举）                          |
| R4 | 无交付物的工作包评分上限 95 分（联动 FR-03 R4）                                                 |
| R5 | **发布前置校验，全部通过才允许"确认发布"**：①有效任务权重合计 = 100% ②合约与评分全部确认完成 ③无录入异常（权重/日期/交付物校验全部通过） |
| R6 | 中心校准提供组内尺度一致性提示：成员得分与组均值偏差 ≥3 分时提示"偏严/偏松，请确认"，提示不拦截发布                          |
| R7 | 中心可退回组长补充依据，退回意见必填并留痕                                                          |

**验收标准**

- Given 组长给"慢SQL治理"评 105 分、交付物已上传，但未填写评分说明，When 点击提交评分，Then 系统拦截并提示"偏离 100 分须说明依据"。
- Given 某工作包未上传交付物，When 组长在评分框输入 100，Then 评分被限制为 95 并提示"交付物未上传，最高 95 分"。
- Given 某成员有效任务权重合计 95%、评分已全部确认，When 中心点击确认发布，Then 系统提示"有效权重合计 95% ≠ 100%，不允许发布"。
- Given 本组已评 3 人、均值 103 分，某成员 95 分，When 校准页加载，Then 显示"评分低于组内均值 8.0 分，请确认是否存在尺度偏严"，且不阻止发布。
- Given 合约存在录入异常（如截止日不在合约月份内），When 中心尝试发布，Then 发布被拦截并列出异常明细。

### FR-07 日报 / 周报上传入口（P1）

### FR-10 部门价值总览与总结（P1）

**描述**：面向部门/中心管理者（center）的「部门工作台」，把成本部门的工作翻译为「可视化、可量化、可总结」的汇报视图；数据全部来自系统留痕与聚合，口径统一可追溯。不依赖 AI（纯规则聚合 + 模板生成）。

**价值标签枚举（可配置）**：`降本增效 / 风险防控 / 质量提升 / 创新探索 / 合规保障 / 支撑保障`；未标注的工作包计「未分类」。

**五大模块**

1. **价值标签（可量化，S1）**：工作包新增 `value_tag` 字段，制定合约时可选填、AI 生成时顺带标注；按价值标签聚合「价值分布」。
2. **效能驾驶舱（可视化，S2）**：部门总览页一屏展示核心指标并可下钻；内含人效与负荷（S5）、大目标达成度总览（S7）。
3. **部门趋势对比（S4）**：部门维度环比 / 同比趋势。
4. **部门风险汇聚（S6）**：部门级风险清单 + 风险月度趋势。
5. **部门总结报告（可总结，S3）**：一键生成四段结构化报告并导出。

**驾驶舱指标**

| 指标 | 定义 |
| --- | --- |
| 本月工作包总数 | 当期全部工作包数 |
| 完成率 | 进度 = 100% 的工作包占比 |
| 风险/逾期数 | 风险 + 逾期工作包数 |
| 大目标达成度 | 进行中大目标的加权进度均值 |
| 人均负荷 | 在办工作包总数 ÷ 在职员工数 |
| 价值分布 | 6 类价值标签的工作包占比（可切换按数量 / 按权重） |

**人效与负荷（S5）**

- 人均完成率 = 已完成工作包数 ÷ 在职员工数。
- 四类任务人力分布：基础履职 / 重点交付 / 治理改善 / 探索突破 的工作包数占比。
- 负荷预警：成员在办工作包数 > 组均值 + 2 标记「超负荷」，< 组均值 − 2 标记「富余」（阈值可配置），仅提示不拦截。

**部门趋势对比（S4）**：部门维度月度趋势，指标含工作包总数 / 完成率 / 风险数 / 人均负荷 / 价值分布；支持环比（上月）与同比（去年同期）切换。

**部门风险汇聚（S6）**：部门级风险清单（成员 / 工作包 / 风险等级 / 截止日 / 剩余天数），按风险等级降序、逾期项置顶；风险月度趋势（当月新增 / 消除风险数）。

**大目标达成度总览（S7）**：所有进行中大目标一屏展示——名称 / 加权进度 / 关联合约数 / 价值标签 / 是否部门年度重点 / 风险项数；可下钻到大目标详情（复用 FR-04）。

**规则**

| 编号 | 规则 |
| -- | --- |
| R1 | 价值标签为可配置枚举，制定合约时可选填；AI 生成工作包时顺带标注；未标注计「未分类」，不阻塞提交 |
| R2 | 驾驶舱 / 趋势 / 风险 / 大目标总览均为服务端聚合计算；指标数值与下钻明细条数必须一致（沿用 FR-05 R5） |
| R3 | 价值分布默认按「工作包数量」聚合，可切换按「权重」聚合 |
| R4 | 总结报告固定四段：本期工作全景 / 价值产出 / 风险与问题 / 下期计划；数据来自留痕与聚合，生成时点快照不可篡改 |
| R5 | 部门总览 / 趋势 / 风险 / 报告仅 center 可见；leader 仅可见本组切片（复用行级权限） |
| R6 | 趋势对比支持环比（上月）与同比（去年同期），无历史数据时展示空态「暂无对比数据」 |
| R7 | 负荷预警阈值可配置（默认：在办数 > 组均值 + 2 超负荷，< 组均值 − 2 富余），仅提示不拦截 |
| R8 | 风险清单按风险等级降序、逾期项置顶；风险等级判定沿用看板口径（FR-05） |

**验收标准**

- Given center 登录打开部门总览，When 加载，Then 一屏展示 6 项指标（工作包总数 / 完成率 / 风险数 / 大目标达成度 / 人均负荷 / 价值分布）。
- Given 本月 20 个工作包中 5 个标记「降本增效」，When 查看价值分布，Then 显示降本增效占比 25%，点击该切片下钻恰好 5 条明细（条数一致）。
- Given center 点击生成总结报告，When 生成，Then 输出四段结构化报告，数据与看板 / 台账一致，可导出。
- Given leader 登录访问部门总览，When 打开，Then 仅返回本组切片，看不到其他组数据。
- Given 存在近 3 个月数据，When 打开部门趋势，Then 展示工作包总数 / 完成率 / 风险数 / 人均负荷趋势，环比 / 同比可切换（S4）。
- Given 某成员在办工作包 8 个、组均值 5 个，When 打开人效视图，Then 该成员标记「超负荷」且提示不拦截（S5）。
- Given 本月 3 个风险项（含 1 逾期），When 打开风险汇聚，Then 风险清单按等级降序、逾期置顶，并展示风险月度趋势（S6）。
- Given 2 个进行中大目标（1 个年度重点），When 打开大目标总览，Then 一屏展示名称 / 加权进度 / 关联合约数 / 价值标签 / 是否年度重点，可下钻到详情（S7）。

### FR-11 部门价值量化与投入产出（P1）

**描述**：在 FR-10 价值标签（定性）基础上，为工作包增加「价值量化」字段，把部门工作从「干了什么」升级为「值多少钱」；部门级汇总为「部门创造价值」与「投入产出比」，支撑成本部门向公司证明价值、向上汇报。

**量化口径表（六类价值标签 → 量化单位，给员工填空抓手）**

| 价值标签 | 量化口径 | 示例 |
| --- | --- | --- |
| 降本增效 | 节省金额（元）或工时（人天） | 数据库降配省 30 万/年 |
| 风险防控 | 规避损失金额（元）或避免事故次数 | 避免 1 次大故障（损失约 50 万） |
| 质量提升 | 返工节省工时（人天） | 联调零缺陷省 3 人天 |
| 创新探索 | 潜在收益金额（元，PoC 结论） | 预计支撑 20% 业务增量 |
| 合规保障 | 避免罚款 / 审计损失（元） | 避免审计扣分 |
| 支撑保障 | 支撑需求数 / 业务线数（个） | 支撑 3 条业务线 12 个需求 |

**规则**

| 编号 | 规则 |
| -- | --- |
| R1 | 价值标签与量化配套：填了价值金额必须选价值标签 + 填测算依据；仅标签不填金额计「未量化」 |
| R2 | 两段式：制定合约时填「预计」价值（月初承诺），月末评分时填「实际」价值（核验后） |
| R3 | 防虚报：价值由员工初填，组长/中心确认后才计入部门汇总；未确认计「待确认」 |
| R4 | 与数据核验联动：「实际」价值须有交付物或平台数据佐证（复用 FR-09 数据核验），无佐证仅算「自报待核验」 |
| R5 | 部门汇总：「部门创造价值」= Σ(确认后的实际价值)；「投入产出比」= 部门创造价值 ÷ 部门人力成本（人力成本 = 成员数 × 约定月成本，可配置） |
| R6 | 金额统一以「元」计；人天/次/个等口径展示原始单位 + 说明，不做强行换算（避免口径失真） |

**验收标准**

- Given 张伟给「慢SQL治理」填预计价值 30 万/年、依据「数据库账单降配 30%」，When 提交，Then 工作包显示价值标签「降本增效」+ 预计 30 万，组长确认后计入部门价值汇总。
- Given 某工作包填了价值金额但未填依据，When 保存，Then 拦截「填写价值金额须附测算依据」。
- Given 月末组长把「慢SQL治理」实际价值核验为 25 万（有账单佐证），When 确认，Then 部门价值汇总以 25 万为准，展示「兑现 83%」。
- Given 部门本月确认价值 60 万、人力成本 50 万，When 查看投入产出，Then 显示投入产出比 1.2（每投入 1 元创造 1.2 元价值）。

### FR-08 个人能力标签自动解析（P2）

**描述**：从个人工作包文本、进度留痕、交付物类型中抽取能力关键词，映射到能力词典，形成个人能力画像；仅用于能力发展辅导，**不参与绩效计分**。

**能力词典（初始 8 类，可配置）**：需求与产品分析能力、Java 后端开发能力、前端开发能力、数据库与 SQL 调优能力、系统架构与治理能力、测试与质量保障能力、项目管理与协同能力、AI 应用与数据能力

**规则**

- R1：标签来源与权重：工作包文本命中 1 分、交付物类型命中 1 分、进度留痕命中 0.5 分；累计得分 ≥2 才生成标签。
- R2：每个标签必须附证据（关联的工作包 ID 列表 + 最近一次出现时间），无证据不展示。
- R3：标签仅员工本人、组长、中心可见；界面固定展示"用于能力发展参考，不参与绩效计分"。
- R4：支持员工手动隐藏/确认标签（隐藏后不再展示，但数据保留）。
- R5：能力词典可导入外部《员工能力评价清单》覆盖默认词表。
- R6：能力标签不写入绩效得分、不进入评分口径，仅作为《能力辅导台账》输入（对齐制度 Q4："能力辅导与 IDP 不计分"）。

**验收标准**

- Given 某员工有 2 个工作包含"慢SQL治理""SQL 调优"且交付物为数据报表，When 打开能力画像，Then 展示"数据库与 SQL 调优能力"标签及其证据列表。
- Given 某标签仅出现 1 次（累计 1 分），When 生成画像，Then 该标签不展示。
- Given 员工点击"隐藏标签"，When 刷新页面，Then 该标签不再展示且不再参与后续推荐。

## 10. 数据模型（开发可直接建表）

| 实体             | 关键字段                                                                                                                                                                   | 说明                                              |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| User           | `id, name, role(employee/leader/center), group_id, join_month`                                                                                                         | 角色决定权限与层级视图                                     |
| Objective（大目标） | `id, name, group_id, owner_id, start_date, end_date, status, progress, is_key` | `progress` 为计算值，非人工填写；`is_key` 是否部门年度重点（0/1，默认 0） |
| Contract       | `id, user_id, month(YYYY-MM), status, submit_at, check_by, score, publish_at`                                                                                          | 一人一月一条                                          |
| ContractItem   | `id, contract_id, objective_id, type, priority(高/中/低), title, target_desc, deliverable_type, deliverable_desc, weight, due_date, progress, source(manual/AI), value_tag, value_amount, value_unit, value_basis, value_type, checked` | `weight` 整数；`objective_id` 三类任务必填；`priority` 必填；`value_tag` 六类价值标签（可空，未标注计未分类）；`value_amount/value_unit/value_basis/value_type` 价值量化（FR-11，可空，填金额时依据必填） |
| Deliverable    | `id, item_id, kind(file/link), file_type, url, uploader, upload_at, version`                                                                                           | 发布后禁止变更                                         |
| ProgressLog    | `id, item_id, operator, raw_text, ai_result(JSON), delta, created_at`                                                                                                  | 原始文本 + 解析结果双留痕                                  |
| ReportEntry    | `id, user_id, kind(daily/weekly), period, content_ref, ai_summary, linked_item_ids, version`                                                                           | 日报/周报                                           |
| ChangeLog      | `id, item_id, field, old_value, new_value, reason, note, operator, created_at`                                                                                         | `reason ∈ {上游调整, 资源不足, 估时不准, 范围蔓延, 临时插入任务}`     |
| SkillTag       | `id, user_id, tag_name, score, evidence_item_ids, updated_at, hidden`                                                                                                  | 不计分                                             |

**状态机（Contract）**

`draft`（草稿）→ `submitted`（待组长核对）→ `confirmed`（执行中）／`rejected`（退回）→ `rated`（待中心校准）→ `published`（已发布，只读）

**校验规则汇总**

| 对象                       | 规则                                 |
| ------------------------ | ---------------------------------- |
| ContractItem.weight      | 1–100 整数；同一 Contract 内合计 = 100     |
| ContractItem.priority    | 枚举：高/中/低，必填（制定时明确，用于资源协调与看板排序）     |
| ContractItem.target_desc | 非空，≤200 字；体检要求含数字与可验证动词            |
| ContractItem.progress    | 0–100 整数；回退需原因                     |
| ContractItem.due_date    | 必须在合约月份内                           |
| Contract.score           | 80–120 整数；无交付物时上限 95               |
| 月度得分                     | `Σ(score × weight) ÷ 100`，保留 1 位小数 |

## 11. AI 能力规格（输入 / 输出 / 兜底）

| 能力   | 输入                    | 输出                                                     | 失败兜底            |
| ---- | --------------------- | ------------------------------------------------------ | --------------- |
| 合约生成 | 口语描述 + 大目标 + 历史合约     | 严格 JSON（见 FR-02）                                       | 降级为模板预填 + 手工新增  |
| 进度解析 | 自然语言文本 + 当月在办工作包      | `{item_id, new_progress, delta, evidence, confidence}` | 降级为手工进度输入框      |
| 报表解析 | 日报/周报文本或文件            | `{summary[], suggestions[{item_id, delta, reason}]}`   | 仅存文件，不解析        |
| 能力标签 | 工作包文本 + 进度留痕 + 交付物类型  | `{tag_name, score, evidence_item_ids[]}`               | 纯关键词规则匹配        |
| 数据核验 | 工作包目标 + 平台数据（Mock/接口） | `{actual, suggest_score, basis}`                       | 展示"暂无法自动核验"，转人工 |

**通用约束**：所有 AI 输出必须为可解析 JSON（schema 校验失败即视为失败）；前端展示 AI 结论时必须标注"AI 生成，请确认"；解析结果一律人工确认后入库（`confidence ≥ 0.85` 且用户开启"自动采纳"时可跳过确认）。

## 12. 交互与主流程

**制定（月初）**：关联大目标 → 口语描述 → AI 生成 3–5 个工作包（含交付物与权重）→ 体检 → 调整 → 权重校验 100% → 提交 → 组长逐条核对（通过/退回+意见）→ 确认合约。

**执行（月中）**：说一句更新进度（AI 解析→确认→入库）｜上传日报周报自动关联｜风险项系统建议 + 月中调整（必填变更原因）→ 大目标进度实时重算。

**验收（月末）**：上传交付物 → 组长自动取数核验 + 评分（无交付物封顶 95）→ 提交评分 → 中心尺度一致性检查 → 确认发布 → 生成月度台账与能力画像。

**异常与空状态**

| 场景     | 表现                           |
| ------ | ---------------------------- |
| 无合约    | "本月暂无合约，创建合约"按钮 + 一句 AI 生成入口 |
| 无大目标可选 | 提示联系中心管理者创建，允许暂存草稿           |
| AI 不可用 | 全流程降级为手工，页面提示不阻塞             |
| 无权访问   | 明确提示"仅本人/本组可见"               |
| 无历史月份  | "该月暂无合约"                     |

## 14. 风险与待确认问题

| 风险/问题                    | 影响 | 缓解方案                              |
| ------------------------ | -- | --------------------------------- |
| AI 解析进度准确率不足，员工不信任       | 高  | 强制人工确认 + 可编辑；展示原文与解析对照；积累反馈日志持续优化 |
| 能力标签被误用于考核               | 中  | 界面固定声明"不参与计分"；仅本人/组长/中心可见         |
| 交付物涉及生产或客户数据             | 高  | 类型白名单 + 大小限制 + 提示语 + 下载鉴权 + 审计留痕  |
| 大目标进度口径存在争议              | 中  | 页面展示计算公式与各包贡献占比，口径唯一且可核对          |
| 真实平台取数对接周期长              | 中  | 定义数据适配层接口契约，先用 Mock 数据，接口就绪后替换    |
| 待确认：能力词典是否采用现有《员工能力评价清单》 | 中  | 需人力/中心确认词表来源与更新机制                 |
| 待确认：评分上限 95 的约束是否为硬拦截    | 低  | 当前设计为"需二次确认 + 填理由"，是否改为硬拦截待定      |

## 15. 发布标准（验收 Checklist）

- [ ] P0 四项全部完成并通过验收：自然语言进度更新、AI 合约生成、交付物上传、大目标关联汇聚
- [ ] 权重合计 = 100% 校验在提交、变更两个入口均生效
- [ ] 评分偏离 100 分未填依据被拦截；评分 >100 无超预期成果证据被拦截；无交付物封顶 95 生效
- [ ] 发布前置校验三项逐项生效：有效权重 100% / 合约与评分全确认 / 无录入异常
- [ ] 交付物缺失时评分上限 95 生效且提示准确
- [ ] 大目标进度公式与页面展示一致（抽 3 组数据手算核对）
- [ ] 看板指标数值与下钻明细条数一致
- [ ] 权限矩阵验证：员工 / 组长 / 中心三角色越权访问均被拦截
- [ ] AI 不可用时全流程可手工走通（断网演练）
- [ ] 操作日志可导出且包含变更原因
- [ ] 按月切换视图只读校验通过
